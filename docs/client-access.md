# Клиентский доступ и необязательное пространство

Администратор пространства назначает роль **Клиент** в настройках участников. После назначения у участника нет доступа к содержимому проектов. В строке клиента кнопка **Доступ** открывает выбор отдельных задач и страниц, поиск по названию и фильтр по проекту. Доступ можно выдать или отозвать для каждого объекта отдельно.

Клиент работает на `/<workspaceSlug>/client`: видит только выданные объекты, их описания, разрешённые файлы и внешние комментарии задач. Редактирование и внутренние комментарии недоступны. Доступ к странице не распространяется на дочерние страницы, связанные задачи, остальные страницы или проект целиком. Обычные API проектов, аналитики, поиска и совместного редактора для клиента закрыты. Полный доступ администраторов пространства и экземпляра сохраняется.

Выдача прав хранится в `ClientAccessGrant`, отдельно от членства в проектах. При переводе существующего участника в клиента прежние проектные членства деактивируются. При смене роли клиента его выдачи удаляются; старые приглашения в проекты не дают обойти ограничения. Удаление объекта, его перенос из проекта, удаление связи страницы с проектом и выход из пространства прекращают доступ. API проверяет актуальные права на основной базе; клиентский экран обновляет список каждые 15 секунд.

Клиентские файлы выдаются через маршрут конкретного разрешения с повторной проверкой объекта. Описания очищаются от исполняемого HTML; изображения редактора используют тот же маршрут проверки файлов. Совместный редактор проверяет доступ каждой сессии и повторяет проверку перед обработкой сообщений.

Регистрацию можно завершить кнопкой **Продолжить без рабочего пространства**, включая экземпляры с запрещённым созданием пространств. Пользователь без пространства попадает на экран приглашений; создать пространство можно позже.

Короткий и длинный логотипы заменены в общих SVG-компонентах, экранах входа и настройки, загрузчиках, favicon/PWA-значках, изображении предпросмотра и почтовых шаблонах. Письма берут PNG логотипа с текущего экземпляра через тег `gizmo_logo_url` и настройки `WEB_URL` / `APP_BASE_URL`.

## Применение

Развернуть API, web, live, admin и space вместе с общими пакетами. В штатном окружении API применить миграции `0134_client_role` и `0135_client_resource_access` командой `python manage.py migrate`, затем запустить новую версию live. Новый live использует API `collaboration-access/`, поэтому API следует обновить раньше live. Проверить раздачу статики логотипов и файлов в рабочем окружении.

Основные маршруты:

- `GET/POST /api/workspaces/<slug>/clients/<client_id>/access/` — администратор: список и выдача.
- `DELETE /api/workspaces/<slug>/clients/<client_id>/access/<grant_id>/` — администратор: отзыв.
- `GET /api/workspaces/<slug>/client-resources/` — собственный список клиента.
- `GET /api/workspaces/<slug>/client-resources/<grant_id>/` — содержимое объекта.
- `GET /api/workspaces/<slug>/client-resources/<grant_id>/files/<asset_id>/` — файл выданного объекта.

Проверки Django в Windows выполняются в изолированном SQLite-окружении с адаптацией PostgreSQL ArrayField. Они не заменяют применение миграций и проверку PostgreSQL, S3, доставки писем и WebSocket в окружении развёртывания.
