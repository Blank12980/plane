# Клиентский доступ и необязательное пространство

> Настройка доступа клиентов теперь находится в разделах **Клиенты** (см. ниже). Кнопки «Доступ» в списке участников больше нет.

Администратор пространства назначает роль **Клиент** в настройках участников. После назначения у участника нет доступа к содержимому проектов.

## Раздел «Клиенты»

Что видит каждый клиент, настраивается в отдельном разделе настроек. Для каждого клиента показано, сколько задач и страниц ему открыто, а кнопка **Настроить доступ** открывает выбор отдельных задач и страниц с поиском по названию. Доступ можно выдать или отозвать для каждого объекта отдельно.

| Кто | Где виден раздел | Что настраивает |
| --- | --- | --- |
| Суперадмин (админ) экземпляра | «Настройки пространства → Клиенты» и «Настройки проекта → Клиенты» во всех пространствах и проектах | всех клиентов во всех проектах |
| Администратор пространства | «Настройки пространства → Клиенты» и «Клиенты» в настройках каждого проекта пространства | всех клиентов пространства, во всех проектах |
| Администратор проекта (не админ пространства) | только «Настройки проекта → Клиенты» своего проекта | доступ клиентов только к объектам этого проекта |
| Участник, гость, клиент | раздела нет, API отвечает 403 | ничего |

Права проверяет Django: запрос списка без `project_id` разрешён только администраторам пространства и экземпляра, а запросы с `project_id`, выдача и отзыв доступа — администратору соответствующего проекта. Администратор проекта не видит и не может изменить выдачи в других проектах.

## Добавление клиентов в проект

В **Настройки проекта → Клиенты** кнопка **Добавить клиента** открывает список клиентов пространства, которых ещё нет
в проекте (с поиском по имени и почте). Выбранные клиенты появляются в списке проекта. Само добавление доступа не даёт:
клиент видит только задачи и страницы, которые администратор откроет ему кнопкой **Настроить доступ**. Если открыть
клиенту задачу или страницу в пространстве, он добавляется в её проект автоматически. Проект показывает только своих
клиентов (добавленных в него или уже имеющих в нём открытые материалы); раздел пространства показывает всех.

- Администратор проекта добавляет клиентов только в свой проект и **не** меняет роли в пространстве.
- Администратор пространства (и экземпляра) дополнительно видит блок «Сделать клиентом участника пространства»: роль
  участника или гостя меняется на «Клиент» (как в списке участников: его проектные членства отключаются, остаётся только
  то, что откроют для него), и он сразу добавляется в проект. Администраторов так превратить нельзя.
- **Убрать из проекта** закрывает доступ клиента ко всему, что открыто в этом проекте. В других проектах доступ остаётся.

Маршруты: `GET /api/workspaces/<slug>/clients/candidates/?project_id=&search=` (кого можно добавить),
`POST /api/workspaces/<slug>/clients/project-links/` (`project_id`, `client_ids`, `promote_member_ids`),
`DELETE /api/workspaces/<slug>/clients/project-links/<client_id>/?project_id=`. Миграция `0141_project_clients` создаёт
таблицу и добавляет в проекты клиентов, у которых уже есть открытые материалы.

Маршруты: `GET /api/workspaces/<slug>/clients/[?project_id=]` — клиенты со сводкой (число задач и страниц), `GET|POST /api/workspaces/<slug>/clients/<client_id>/access/` и `DELETE .../access/<grant_id>/` — выдачи (с `project_id` ограничиваются проектом).

Клиент работает на `/<workspaceSlug>/client`: видит только выданные объекты, их описания, разрешённые файлы и внешние комментарии задач. Редактирование и внутренние комментарии недоступны. Доступ к странице не распространяется на дочерние страницы, связанные задачи, остальные страницы или проект целиком. Обычные API проектов, аналитики, поиска и совместного редактора для клиента закрыты. Полный доступ администраторов пространства и экземпляра сохраняется.

Выдача прав хранится в `ClientAccessGrant`, отдельно от членства в проектах. При переводе существующего участника в клиента прежние проектные членства деактивируются. При смене роли клиента его выдачи удаляются; старые приглашения в проекты не дают обойти ограничения. Удаление объекта, его перенос из проекта, удаление связи страницы с проектом и выход из пространства прекращают доступ. API проверяет актуальные права на основной базе; клиентский экран обновляет список каждые 15 секунд.

Клиентские файлы выдаются через маршрут конкретного разрешения с повторной проверкой объекта. Описания очищаются от исполняемого HTML; изображения редактора используют тот же маршрут проверки файлов. Совместный редактор проверяет доступ каждой сессии и повторяет проверку перед обработкой сообщений.

При настройке профиля пользователю больше не предлагается создать пространство: создание необязательно и выполняется с главной панели. Онбординг состоит из шагов профиля; шаг приглашений показывается, только если у пользователя есть приглашения. Пользователь без пространств попадает на главную панель (`/invitations`): там список приглашений и карточка «Создать рабочее пространство» (если создание не запрещено администратором экземпляра). У пользователей с пространствами создание доступно в меню пространства.

Короткий и длинный логотипы заменены в общих SVG-компонентах, экранах входа и настройки, загрузчиках, favicon/PWA-значках, изображении предпросмотра и почтовых шаблонах. Письма берут PNG логотипа с текущего экземпляра через тег `gizmo_logo_url` и настройки `WEB_URL` / `APP_BASE_URL`.

## Применение

Развернуть API, web, live, admin и space вместе с общими пакетами. В штатном окружении API применить миграции `0134_client_role` и `0135_client_resource_access` командой `python manage.py migrate`, затем запустить новую версию live. Новый live использует API `collaboration-access/`, поэтому API следует обновить раньше live. Проверить раздачу статики логотипов и файлов в рабочем окружении.

Основные маршруты:

- `GET/POST /api/workspaces/<slug>/clients/<client_id>/access/` — администратор: список и выдача.
- `DELETE /api/workspaces/<slug>/clients/<client_id>/access/<grant_id>/` — администратор: отзыв.
- `GET /api/workspaces/<slug>/client-resources/` — собственный список клиента.
- `GET /api/workspaces/<slug>/client-resources/<grant_id>/` — содержимое объекта.
- `GET /api/workspaces/<slug>/client-resources/<grant_id>/files/<asset_id>/` — файл выданного объекта.

Проверки Django в Windows выполняются в изолированном SQLite-окружении с адаптацией PostgreSQL ArrayField. Они не заменяют применение миграций и проверку PostgreSQL, S3, доставки писем и WebSocket в окружении развёртывания.
